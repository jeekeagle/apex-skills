# I/O Schema(Hermes 版)

## 输入

### 触发信号

用户消息中包含以下任一信号即触发本 skill:

| 信号类型 | 例子 |
| --- | --- |
| 显式触发 | "帮我润色一下" / "润色一下" / "改一下这段" |
| 动作描述 | "整理成周报" / "整理成会议纪要" / "改成朋友圈" |
| 抱怨型 | "这段太口语了" / "我说的很乱,理一下" / "帮我捋顺" |
| 隐式触发 | 用户消息里贴了一段明显是口述/转写的内容,自己说"看看怎么改" |

### 原料(必填)

**润色必须基于用户自己写/说的内容。** 原料来源有三种:

1. **用户消息里直接附带** — 主推(Hermes 没有时间线,这是默认路径)
2. **用户上一条消息的内容** — 如果用户在同一个对话里刚刚说了一段,可以润色那段
3. **用户提供的文件路径** — 如果用户说"我刚记的笔记在 X",用 read_file 读;但**必须先告诉用户你要去读他的哪个文件**,不要默默翻

### 原料的合格判定

| 原料类型 | 是否可润色 | 原因 |
| --- | --- | --- |
| 用户自己写的笔记 | ✅ | 用户自己的表达 |
| 用户自己录的音(转写文本) | ✅ | 用户自己的表达 |
| 用户日记 / 反思 | ✅ | 用户自己的表达 |
| 用户保存的公众号文章 | ❌ | 不是用户的表达,是摘要场景 |
| 用户保存的书摘 / 课程原文 | ❌ | 不是用户的表达 |
| 用户复述别人的话 | ⚠️ | 看用户是否要署名——如果要署名润色(改成自己的话),用 humanizer 改写更合适 |
| AI 之前给用户写的稿子 | ❌ | 那是改稿,不是润色用户的表达 |

**判断标准:用户愿不愿意以"我写的"发出去。** 愿意 → 润色;不愿意 → 不是润色场景。

### 原料太短的判定

| 长度 | 处理 |
| --- | --- |
| < 20 字且无语义空间(如"嗯""好的""记一下") | 走"用户输入太短"兜底 |
| 20-50 字但语义完整(如"今天有点累") | 可以润色,但长度铁律是 30-50 字,不要硬撑 |
| > 50 字 | 正常润色,长度按内容性质走 |

## 输出

### 形式

**聊天消息。** 直接以消息正文回出,无文件、无卡片、无附件。

### 消息结构(单条)

```
[一两句话说改了什么(种子锚点)]

[润色后的完整成品]
```

种子锚点**必须有**,成品**必须有**,**两者不能混在同一个段落里**。

### 种子锚点模板

| 内容性质 | 种子锚点模板 |
| --- | --- |
| 录音 | "你刚录的这段——我帮你捋了一下" |
| 笔记 | "你记的这条——" |
| 对话 | "你说的这段——" |
| 多源 | "你那几条内容我合并整理了一下" |
| 没指明来源 | "你这段——" |

种子锚点**只说一句**,不展开。用户不想听"我帮你分析了你的语言结构,主要去除了 12 个冗余表达"——用户想听"主要把因果理顺了"。

### 长度契约

| 输入长度 | 输出长度 | 说明 |
| --- | --- | --- |
| 用户 50 字 | 30-50 字 | 更精炼 |
| 用户 200 字 | 150-200 字 | 更清楚 |
| 用户 10 分钟录音 | 300-600 字 | 提取+结构化 |
| 用户 1 小时会议 | 500-1000 字 | 会议纪要 |
| 用户 30 字感想 | 不润色,走兜底 | "有点意思"比硬写一段更真实 |

**长度铁律:润色产出 ≤ 原料长度 × 1.5**(长录音的提取+结构化除外,那种 1 小时 → 1000 字是合理的浓缩)。

### 退场约定

润色发出去就退。**绝对不要**在润色后追加:

- "还需要调整吗?"
- "要再短一点吗?"
- "你看这样行不行"
- "如果想往 X 方向调,可以告诉我"
- 列 3 个备选版让用户挑

用户想继续调,自己会说。2 轮上限:用户追问"再调一下"→ 再追 1 条;用户不响应 → 对话结束。

## 边界 case 处理

### Case 1:用户说"润色一下"但没附内容

**不要去翻文件、不要去对话历史里找**。直接说:

> "你把要润色的内容发我一下,我直接帮你捋。"

**为什么不去翻:** Hermes 对话上下文不可靠,翻用户文件更不可靠(用户可能没想润色那条)。告诉用户贴原文最稳。

### Case 2:用户给了内容但明显是别人写的

> 【用户输入】 "帮我润色一下这段: <一段乔布斯传里的引文>"

**回复:**

> "这段是别人写的,不是你说的——润色是帮你的话变清楚,改别人的话不算。要是你想改写成自己的版本,告诉我,我帮你。"

### Case 3:用户给了 AI 之前写的稿子要"润色"

> 【用户输入】 "你上次给我写的那个介绍改一下"

**回复:**

> "上次那个是 AI 写的——直接改,改完还是 AI 腔。要不你把想表达的意思用你自己的话再说一遍,我帮你捋成自己的版本?"

(或者让 humanizer skill 上场)

### Case 4:用户内容信息密度太低

> 【用户输入】 "嗯,听完了,感觉有点意思。"

**回复:**

> "这句话本身就挺完整的——'有点意思'四个字比写一段感悟更真实。等你想多说两句的时候,来找我帮你理。"

### Case 5:用户同时给了多条互不相关的内容

**不要**硬合并成一篇(违背"按主题/角色归类"原则)。

**回复:**

> "你给的这两条主题不一样,我分开润色,你看哪条先来?"

### Case 6:用户给的录音转写明显有错(人名 / 数字 / 时间听错)

**不要默默改对。** 标注出来:

> "我标了两个我没把握的地方:那个数字我听不太清,改成了 X,你看对不对;那个人名我没认出,是 Y 吗?"

或者在润色版里用 [?张三?] 标注。

### Case 7:用户要"润色成莎士比亚风格" / "润色得文艺点"

**拒绝。** 润色的标准是清顺准简,不是华丽。如果用户坚持要"更高级",告诉他润色不干这个,推荐他去看其他工具或者自己改。

### Case 8:用户说"润色完顺便起个标题"

**可以,但要明示是用户没说的内容。** 标题用户没给过,你加了一个——这是边界动作,要做就做但要标:

> "你这段我帮你捋顺了,另外起了个标题,你看看合不合适。"

(用户没要求起标题时不要主动加,默认不加。)

## 与其他 skill 的边界

| Skill | 区别 |
| --- | --- |
| `humanizer` | 对象是 AI 写出来的稿子(去 AI 腔);polish-get 对象是用户自己的话(去口水词 + 理结构) |
| `chinese-analytical-article` | 对象是零 → 生成深度长文;polish-get 对象是用户的碎片 → 整理成文 |
| `make-seed` | 跨领域联想往外碰;polish-get 严格不离开用户说过的话 |
| `ask-get` (拷问) | 找用户推理的漏洞;polish-get 严守用户原意 |

**触发冲突时:** 如果用户既触发了润色又触发了其他 skill,默认走润色(用户的明确意图);除非用户说"顺便拷问一下" / "顺便联想一下"。

## 不在润色范围内的事项

这些明确不做,告诉用户去找对应的 skill / 工具:

- 给文章配图 → 走 baoyu-article-illustrator
- 翻译成英文 / 其他语言 → 走翻译
- 校对错别字(不改结构) → 简单的 proofread
- 给长文加摘要 → 摘要场景,不是润色
- 从零写一篇新文章 → 写作场景
- 给会议加待办提醒 → 走 productivity 工具
- 校对论文格式 / 参考文献 → 走学术写作
